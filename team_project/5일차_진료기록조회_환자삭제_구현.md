## 3. 진료기록 조회 API 구현 (⑦⑧⑨)

### 3-1. 파일 구성

| 계층 | 파일 | 추가 내용 |
|---|---|---|
| API | `apis/medical_record_apis.py` | 조회 API 3개, 이미지 응답 헤더 |
| 서비스 | `services/medical_record_service.py` | `list_by_patient`, `get_detail`, `get_xray_file` |
| 저장소 | `repositories/medical_record_repository.py` | `list_by_patient`, `get_with_image`, `get_image`, `exists` |
| 스키마 | `schemas/medical_record.py` | `MedicalRecordListItem`, `summarize_symptoms`, 시간 필드 `UTCDateTime` |

### 3-2. ⑦ 목록: 증상 100자 요약

정의서의 "증상 100자 초과 시 … 생략"을 **글자 수 기준**으로 구현했다. 바이트 기준이면 한글은 1글자가 3바이트라 33자에서 잘린다.

| 입력 | 응답 |
|---|---|
| 정확히 100자 | 그대로 |
| 101자 이상 | 앞 100자 + `…` |
| 기록 없는 환자 | `[]` (200) |
| 없는 환자 | 404 `환자를 찾을 수 없습니다.` |

DB 원문은 바꾸지 않고 응답에서만 자른다. 정렬은 최신순(`created_at desc, id desc`)이다.

### 3-3. ⑧ 상세: 한 번의 조회로 업로더 이름까지

진료기록, X-Ray 이미지, 업로더 이름을 **쿼리 한 번**으로 가져온다. 업로더가 탈퇴하면 `uploader_id`가 `SET NULL`이 되므로 **외부 조인(outer join)**을 써야 기록이 사라지지 않는다.

```python
select(MedicalRecord, XrayImage, User.name)
    .join(XrayImage, XrayImage.record_id == MedicalRecord.id)
    .outerjoin(User, User.id == XrayImage.uploader_id)   # 탈퇴한 업로더도 기록은 조회
    .where(MedicalRecord.id == record_id)
    .order_by(XrayImage.id.desc())
    .limit(1)
```

응답의 `xray_image_url`은 실제 저장 위치가 아니라 **⑨ 이미지 API 경로**다. 파일이 서버 어디에 있는지 외부에 노출하지 않는다.

### 3-4. ⑨ X-Ray 이미지: 비공개 저장소 + 경로 검증

X-Ray는 의료 정보라 공개 폴더(`/media`)에 두지 않고, **로그인한 스태프만** 이 API로 받을 수 있게 했다.

```python
try:
    path = resolve_xray_path(image.image_url)
except ValueError:
    # 저장 폴더 밖을 가리키는 값: 이유를 숨기고 404, 로그에는 이미지 ID만 남긴다
    logger.warning("저장 폴더 밖 X-Ray 경로가 조회됨: xray_image_id=%s", image.id)
    raise HTTPException(status_code=404, detail=IMAGE_NOT_FOUND)
```

| 상황 | 응답 | 이유 |
|---|---|---|
| 정상 | 200 + 이미지 | |
| 기록은 있는데 이미지 없음 | 404 `이미지 파일을 찾을 수 없습니다.` | |
| 기록 없음 | 404 `진료기록을 찾을 수 없습니다.` | |
| `../../`처럼 저장 폴더 밖 경로 | 404 (이유 숨김) | 공격자에게 힌트를 주지 않기 위해 |
| 파일 없음, 허용 안 된 확장자 | 404 | |

응답 헤더도 의료 이미지에 맞게 지정했다.

```python
XRAY_RESPONSE_HEADERS = {
    "Content-Disposition": "inline",        # 다운로드가 아니라 화면에 표시
    "Cache-Control": "private, no-store",   # 브라우저·프록시에 의료 이미지 캐시 금지
    "X-Content-Type-Options": "nosniff",    # 내용을 추측해 다른 형식으로 실행하는 것 차단
}
```

### 3-5. 시간 표기 통일 (`Z`)

진료기록 응답의 `created_at`, `updated_at`을 공통 타입 `UTCDateTime`으로 바꿔 `2026-10-27T09:18:34Z`처럼 UTC임을 표시했다. 다른 담당자를 기다리지 않고 내 PR에서 바꿔, 등록(⑥)·상세(⑧) 응답이 함께 통일되었다.

## 4. 인증 이미지 화면 표시 (Blob)

### 4-1. 문제

이미지 API는 `Authorization` 헤더가 있어야 열린다. 그런데 `<img src="...">`는 **헤더를 붙일 수 없다.** 토큰을 URL에 붙이면(`?token=...`) 브라우저 기록·서버 로그에 토큰이 남는다.

### 4-2. 해결: fetch → Blob → Object URL

| 단계 | 파일 | 내용 |
|---|---|---|
| ① | `static/apis.js` | `getXrayImage()`: 토큰을 **헤더에** 담아 요청하고 `Blob`으로 받음. 토큰 만료 시 기존 재발급 로직도 그대로 적용 |
| ② | `static/pages.js` | `URL.createObjectURL(blob)`으로 임시 주소를 만들어 `<img>`에 표시 |
| ③ | `static/app.js` | 화면을 이동할 때 `URL.revokeObjectURL()`로 임시 주소 해제 (메모리 누수 방지) |

```js
async loadXrayImage(imageUrl) {
    const img = document.getElementById('xray-img');
    this.releaseXrayImage();                       // 이전 이미지 주소 해제
    try {
        const blob = await apis.getXrayImage(imageUrl);
        this.currentXrayUrl = URL.createObjectURL(blob);
        img.src = this.currentXrayUrl;
    } catch (err) {
        img.removeAttribute('src');
        img.alt = 'X-Ray 이미지를 불러오지 못했습니다.';
    }
},
```

`request()` 함수가 `responseType` 옵션을 `fetch`에 그대로 넘기지 않도록 분리하고, `'blob'`일 때만 `response.blob()`을 반환하게 고쳐 기존 JSON API에 영향이 없게 했다.

## 5. 환자 상세·수정·삭제 구현 (③④⑤)

3번 담당자가 공백이 되어, 4번 작업을 Merge한 뒤 이어서 맡았다. 진료기록 파일은 건드리지 않고 **환자 파일만** 수정해서, 동시에 진행 중이던 #30과 충돌이 나지 않게 했다.

### 5-1. ③ 상세, ④ 수정

| API | 처리 |
|---|---|
| ③ 상세 | 공통 `get_or_404()`로 조회, 없으면 404 |
| ④ 수정 | 이름·연락처만 부분 수정 (`model_dump(exclude_unset=True)`) |

| 수정 요청 | 응답 | 이유 |
|---|---|---|
| `{"name": "김수정"}` | 200, 이름만 변경, `updated_at` 갱신 | 보내지 않은 필드는 유지 |
| `{}` | 400 `수정할 항목을 하나 이상 입력하세요.` | 아무것도 안 바꾸는 요청 거부 |
| `{"age": 50}` | 422 | 나이·성별은 수정 불가 (`extra="forbid"`) |
| `{"name": null}` | 422 | 그대로 두면 NOT NULL 컬럼에 NULL이 들어가 500이 됨 |

### 5-2. ⑤ 삭제: DB와 파일을 함께 지우는 순서

환자를 지우면 진료기록·X-Ray·AI 결과 행은 DB의 `ON DELETE CASCADE`로 사라진다. 하지만 **서버에 저장된 이미지 파일은 DB가 지워 주지 않는다.** 그래서 순서를 설계 문서(6-3, 6-4)대로 지켰다.

```text
① 환자 행 잠금 (SELECT ... FOR UPDATE)  ← 등록·수정과 순서를 맞춤 (환자 → 진료기록)
② 지울 파일 경로 수집 (X-Ray + AI 히트맵)
③ 환자 삭제 + 파일 정리 작업 기록  → 하나의 트랜잭션으로 commit
④ commit 후 실제 파일 삭제, 빈 환자 폴더 정리
⑤ 파일 삭제 실패 → 작업 보존 + 500 / DELETE 재요청 → 남은 작업 이어서 정리 → 204
```

| 결정 | 이유 |
|---|---|
| **DB 먼저, 파일 나중** | 파일을 먼저 지웠는데 DB 삭제가 실패하면, 기록은 있는데 이미지가 없는 상태가 된다 |
| **정리 작업을 같은 트랜잭션에 기록** | commit 후 서버가 멈춰도 "어떤 파일을 지워야 하는지"가 DB에 남아 재처리할 수 있다 |
| **재요청 시 이어서 정리** | 파일 삭제가 실패한 뒤 다시 DELETE를 보내면, 환자는 이미 없어도 남은 파일을 마저 지우고 204를 준다. 모두 끝난 뒤에는 404 |
| **공통 `FileCleanupService` 사용** | 진료기록 삭제·이미지 교체와 같은 방식으로 파일을 정리해 팀 코드를 일관되게 유지 |

## 6. 코드 리뷰 반영

PR #32에서 리뷰 지적 2건을 받아 같은 PR에 반영했다.

| 구분 | 지적 | 원인 | 수정 |
|---|---|---|---|
| **P1** | 동시에 등록·교체가 일어나면 이미지 파일이 남을 수 있다 | MySQL 기본 격리 수준(REPEATABLE READ)에서 일반 `SELECT`는 **트랜잭션 시작 시점의 스냅샷**을 읽는다. 환자 잠금을 기다리는 사이 새로 등록된 이미지 경로를 놓칠 수 있다 | 파일 경로 조회 2곳에 `.with_for_update()`를 적용했다. **잠금 읽기**는 항상 최신 데이터를 읽는다 |
| **P2** | 정리 작업 저장 실패 시 `text/plain` 500이 나간다 | `cleanup.run()`, `cleanup.resume()`이 예외 처리 밖에 있었다 | DB 예외를 잡아 rollback하고, 설계된 JSON 500(`파일 정리가 완료되지 않았습니다…`)을 반환했다 |

테스트 3개를 추가해 검증했다: 상태 저장 실패, 재개 실패, `FOR UPDATE` 적용 여부.

> 환자 잠금만 걸면 충분하다고 생각했지만, **잠금을 얻는 것과 최신 데이터를 읽는 것은 별개**라는 점을 리뷰로 배웠다.

## 9. 배운 점

- **의료 이미지는 "보여주는 방법"까지 보안이다**: 공개 폴더에 두지 않고, 인증 API·캐시 금지·nosniff 헤더·경로 검증까지 갖춰야 안전하다.
- **`<img>`는 헤더를 못 보낸다**: 인증이 필요한 이미지는 `fetch` → `Blob` → Object URL로 표시하고, 다 쓴 주소는 `revokeObjectURL`로 해제한다.
- **DB 삭제와 파일 삭제는 원자적이지 않다**: DB를 먼저 commit하고, 지울 파일 목록을 같은 트랜잭션에 남겨야 실패해도 복구할 수 있다.
- **잠금을 얻는 것 ≠ 최신 데이터를 읽는 것**: REPEATABLE READ에서는 잠금 읽기(`FOR UPDATE`)를 써야 다른 트랜잭션이 방금 넣은 행까지 본다.
- **협업은 충돌을 줄이는 설계부터**: 같은 파일을 여러 명이 고치면 충돌은 피할 수 없다. 담당 파일을 나누고, 충돌이 나면 양쪽 의도를 모두 살리는 쪽으로 합친다.
