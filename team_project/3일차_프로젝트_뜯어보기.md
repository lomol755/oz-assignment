## 0. 아키텍처 개요

### 0-1. 계층형 아키텍처 (Layered Architecture)

이 템플릿은 **계층형 아키텍처**를 따른다. 애플리케이션을 역할별 계층(Layer)으로 나누고, **각 계층은 바로 아래 계층에만 의존**하도록 설계하는 방식이다.

```
                    HTTP Request
                         │
┌────────────────────────▼────────────────────────┐
│  Presentation Layer   app/apis/                 │  URL 라우팅, 요청·응답 처리
│                       app/schemas/              │  데이터 형식 검증 (DTO)
├─────────────────────────────────────────────────┤
│  Business Layer       app/services/             │  비즈니스 규칙, 흐름 제어
├─────────────────────────────────────────────────┤
│  Persistence Layer    app/repositories/         │  DB 접근 (CRUD 쿼리)
│                       app/models/               │  테이블 정의 (ORM Entity)
├─────────────────────────────────────────────────┤
│  Infrastructure       app/core/                 │  설정, DB 엔진·세션, 공통 Mixin
└────────────────────────┬────────────────────────┘
                         ▼
                   MySQL Database
```

### 0-2. 왜 계층을 나누는가

| 원칙 | 설명 | 이 프로젝트에서의 효과 |
|---|---|---|
| **관심사의 분리** (Separation of Concerns) | 하나의 모듈은 하나의 책임만 가진다 | "DB 쿼리는 repositories, 검증 규칙은 services"처럼 코드 위치가 예측 가능해진다 |
| **변경의 국소화** | 한 계층의 변경이 다른 계층으로 번지지 않는다 | DB를 MySQL → PostgreSQL로 바꿔도 repositories만 수정하면 된다 |
| **테스트 용이성** | 계층별로 독립적인 테스트가 가능하다 | service를 테스트할 때 실제 DB 대신 가짜 repository를 넣을 수 있다 |
| **협업 효율** | 팀원이 서로 다른 파일을 수정한다 | 2일차처럼 한 파일(`practice_apis.py`)을 여럿이 고칠 때 발생한 충돌이 줄어든다 |

> 🍽️ **비유로 이해하기: 레스토랑**
> 홀 직원(`apis`)은 주문서 양식(`schemas`)에 맞게 주문을 받고, 셰프(`services`)는 레시피에 따라 요리를 결정하며, 창고 관리인(`repositories`)은 선반 배치도(`models`)에 따라 재료를 꺼내 온다. 홀 직원이 창고에 직접 들어가지 않듯이, **각 계층은 자기 역할 밖의 일을 하지 않는다.**

## 1. 디렉터리별 역할과 작성할 내용

### 1-1. 요약

| 디렉터리 | 계층 | 핵심 질문 | 작성할 파일 예시 |
|---|---|---|---|
| `app/core/` | Infrastructure | 앱 전체가 공유하는 기반은 무엇인가? | `config.py`, `db/databases.py`, `db/models.py` |
| `app/models/` | Persistence | DB 테이블은 어떤 구조인가? | `user.py`, `patient.py`, `xray_record.py` |
| `app/repositories/` | Persistence | DB에서 데이터를 **어떻게** 읽고 쓰는가? | `user_repository.py` |
| `app/schemas/` | Presentation | API가 **어떤 형식**의 데이터를 주고받는가? | `user.py` (`UserCreateRequest`, `UserResponse`) |
| `app/services/` | Business | 이 요청을 **처리해도 되는가?** 어떤 순서로 처리하는가? | `user_service.py` |
| `app/apis/` | Presentation | 어떤 **URL과 HTTP 메서드**로 기능을 제공하는가? | `user_api.py`, `patient_api.py` |

> **네이밍 규칙 제안**: 도메인(기능) 단위로 각 계층에 같은 이름의 파일을 둔다.
> 예) 회원 기능 → `models/user.py`, `schemas/user.py`, `repositories/user.py`, `services/user.py`, `apis/user.py`
> 이렇게 하면 "회원 기능의 DB 쿼리"를 찾을 때 `repositories/user.py`로 바로 이동할 수 있다.

### 1-2. `app/core/` — 공통 기반 (Infrastructure)

애플리케이션 전체에서 공유하는 설정과 인프라 코드를 둔다. **비즈니스 로직은 포함하지 않는다.**

```
app/core/
├── config.py          # 환경 변수 기반 설정 (Settings)
└── db/
    ├── databases.py   # DB 엔진, 세션 팩토리, Base, 세션 의존성 함수
    └── models.py      # 여러 모델이 공유하는 공통 컬럼 (Mixin)
```

- 템플릿에 이미 작성되어 있으며, 팀원 대부분은 **가져다 쓰기만** 한다.
- 이후 JWT 인증, 비밀번호 해싱, 공통 예외 처리 같은 공용 기능이 추가될 위치이기도 하다. (예: `core/security.py`, `core/exceptions.py`)

### 1-3. `app/models/` — DB 테이블 정의 (ORM Entity)

**SQLAlchemy ORM**을 사용해 DB 테이블을 파이썬 클래스로 정의한다. 클래스 1개 = 테이블 1개, 클래스 속성 1개 = 컬럼 1개에 대응한다.

```python
# app/models/user.py
class User(UUIDMixin, TimestampMixin, Base):
    __tablename__ = "users"

    email: Mapped[str] = mapped_column(String(50), unique=True)
    password: Mapped[str] = mapped_column(String(255))
```

| 작성할 내용 | 설명 |
|---|---|
| 테이블명 | `__tablename__` (복수형 snake_case 권장: `users`, `xray_records`) |
| 컬럼 | 타입, 길이, `nullable`, `unique`, `default` |
| 관계 | `ForeignKey`(DB 레벨 연결), `relationship()`(파이썬 객체 레벨 연결) |
| 공통 컬럼 | `core/db/models.py`의 Mixin 상속 |

⚠️ 새 모델을 만들면 반드시 `app/models/__init__.py`에 import를 추가해야 Alembic이 인식한다. ([4-3 참고](#4-3-modelsinit_py에-모델-등록-필수))

### 1-4. `app/schemas/` — 요청·응답 데이터 형식 (DTO)

**Pydantic**을 사용해 API가 주고받는 데이터의 형식을 정의하고 자동으로 검증한다. 이런 객체를 **DTO(Data Transfer Object)** 라고 부른다.

```python
# app/schemas/user.py
class UserCreateRequest(BaseModel):      # 요청: 클라이언트 → 서버
    email: EmailStr
    password: str = Field(min_length=8, max_length=20)

class UserResponse(BaseModel):           # 응답: 서버 → 클라이언트
    uuid: UUID
    email: str
    model_config = ConfigDict(from_attributes=True)   # ORM 객체 → 스키마 변환 허용
```

| 작성할 내용 | 설명 |
|---|---|
| 요청 스키마 | `~CreateRequest`, `~UpdateRequest` — 입력값 타입·길이·형식 검증 |
| 응답 스키마 | `~Response` — 클라이언트에 노출할 필드만 정의 |
| `from_attributes=True` | SQLAlchemy 모델 객체를 응답 스키마로 바로 변환하기 위한 설정 |

#### `models` vs `schemas` 비교

| 구분 | `models/` | `schemas/` |
|---|---|---|
| 라이브러리 | SQLAlchemy | Pydantic |
| 표현 대상 | **DB에 저장되는** 데이터 | **API로 주고받는** 데이터 |
| 비밀번호 | 해시값을 컬럼으로 저장 | 요청 스키마에만 존재, **응답 스키마에서는 제외** |
| 개수 | 테이블당 1개 | 용도별로 여러 개 (생성·수정·응답) |

> **왜 분리하는가?** DB 구조를 그대로 API로 노출하면 비밀번호 같은 민감 정보가 새어 나가고, DB 컬럼을 바꿀 때마다 API 명세도 함께 깨진다. 스키마는 **DB와 외부 세계 사이의 방화벽** 역할을 한다.
> 2일차 practice API에서 `response_model=UserResponse`로 password를 응답에서 제외한 것이 바로 이 원리다.

### 1-5. `app/repositories/` — DB 접근 (Data Access)

DB와 직접 대화하는 코드를 모아 둔다. **SQL(쿼리)은 이 계층에서만 작성**한다.

```python
# app/repositories/user.py
async def get_by_email(db: AsyncSession, email: str) -> User | None:
    result = await db.execute(select(User).where(User.email == email))
    return result.scalar_one_or_none()
```

| 작성할 내용 | 예시 함수 |
|---|---|
| 조회 (Read) | `get_by_id()`, `get_by_email()`, `get_list()` |
| 생성 (Create) | `create()` |
| 수정 (Update) | `update()` |
| 삭제 (Delete) | `delete()`, `soft_delete()` |

- 비즈니스 판단(예: "중복이면 에러")은 하지 않는다. **요청받은 데이터를 정확히 읽고 쓰는 것**에만 집중한다.

### 1-6. `app/services/` — 비즈니스 로직

"이 요청을 처리해도 되는가?", "어떤 순서로 처리하는가?"를 결정한다. 여러 repository를 조합해 하나의 업무 흐름을 완성한다.

```python
# app/services/user.py
async def signup(db: AsyncSession, body: UserCreateRequest) -> User:
    if await user_repository.get_by_email(db, body.email):           # ① 규칙 검사
        raise HTTPException(409, "이미 사용 중인 이메일입니다.")
    hashed = hash_password(body.password)                              # ② 가공
    return await user_repository.create(db, body.email, hashed)        # ③ 저장 위임
```

| 작성할 내용 | 예시 |
|---|---|
| 중복·존재 여부 검사 | 이메일 중복, 환자 존재 여부 |
| 권한 확인 | 본인 또는 관리자만 수정 가능 |
| 데이터 가공 | 비밀번호 해싱, 판독 결과 계산 |
| 여러 작업의 조합 | 환자 등록 + 판독 기록 생성 |

#### `services` vs `repositories` 비교

| 구분 | `services/` | `repositories/` |
|---|---|---|
| 핵심 질문 | **무엇을** 할 것인가 (What / Whether) | **어떻게** 저장·조회할 것인가 (How) |
| 예시 | "이메일이 이미 있으면 거절한다" | "`email = ?`인 행을 조회한다" |
| DB 직접 접근 | ❌ repository를 통해서만 | ✅ |
| HTTP 예외 발생 | ✅ (규칙 위반 시) | ❌ |

### 1-7. `app/apis/` — 라우터 (Endpoint)

`APIRouter`로 URL과 HTTP 메서드를 정의한다. **얇게(Thin) 유지**하는 것이 원칙으로, 요청을 받아 service에 넘기고 결과를 응답 스키마로 반환하는 역할만 한다.

```python
# app/apis/user.py
router = APIRouter(prefix="/api/v1/users", tags=["users"])

@router.post("", response_model=UserResponse, status_code=201)
async def signup(body: UserCreateRequest, db: AsyncSession = Depends(async_get_db)):
    return await user_service.signup(db, body)
```

| 작성할 내용 | 설명 |
|---|---|
| `prefix`, `tags` | URL 공통 접두어, Swagger 그룹명 |
| 엔드포인트 함수 | HTTP 메서드, 경로, 상태 코드, `response_model` |
| 의존성 주입 | `Depends(async_get_db)`로 DB 세션을 주입받음 |

> **URL 규칙**: `main.py`의 `catch_all`이 `api/v1`로 시작하는 경로를 예외 처리하고 있으므로, 모든 API는 **`/api/v1/...` 접두어**를 사용한다.

## 2. 주요 파일의 역할

### 2-1. `app/main.py` — 애플리케이션 진입점 (Entry Point)

FastAPI 애플리케이션 객체를 생성하고, 라우터·정적 파일·공통 엔드포인트를 등록하는 **조립 공장**이다.

| 구성 요소 | 역할 |
|---|---|
| `app = FastAPI()` | 애플리케이션 인스턴스 생성 |
| `app.include_router(...)` | `apis/`의 라우터 등록 |
| `app.mount("/static", ...)` | CSS·JS 등 정적 파일 서빙 |
| `app.mount("/media", ...)` | 사용자 업로드 파일(X-Ray 이미지 등) 서빙 |
| `GET /healthcheck` | 서버 생존 확인 (docker-compose의 healthcheck가 호출) |
| `GET /` | 프론트엔드 진입 페이지(`index.html`) 반환 |
| `GET /{path:path}` (`catch_all`) | 등록되지 않은 모든 경로에 `index.html` 반환 (SPA 라우팅 지원) |

```bash
uv run uvicorn app.main:app --reload
#               └──┬──┘ └┬┘
#      app/main.py 모듈   그 안의 app 객체
```

> ⚠️ **라우터 등록 순서**: FastAPI는 **등록된 순서대로** 경로를 매칭한다. `catch_all`은 모든 경로를 받아버리므로, `include_router()`는 반드시 `catch_all`보다 **위에서** 호출해야 한다. 아래에 두면 Swagger에는 API가 보이지만 실제 GET 요청에는 HTML이 응답된다.

### 2-2. `app/core/config.py` — 환경 설정 관리

```python
class Settings(BaseSettings):
    DB_USER: str = "root"
    DB_PASSWORD: str = "password1234"
    DB_HOST: str = "localhost"
    DB_PORT: str = "3306"
    DB_NAME: str = "ai_health"

    model_config = {"env_file": ".env", "extra": "ignore"}

settings = Settings()
```

| 요소 | 설명 |
|---|---|
| `BaseSettings` | `pydantic-settings` 제공. **환경 변수와 `.env` 파일을 읽어** 클래스 속성에 자동 주입 |
| 우선순위 | ① OS 환경 변수 → ② `.env` 파일 → ③ 클래스에 적힌 기본값 |
| `extra: "ignore"` | `.env`에 클래스에 없는 값(예: `DB_ROOT_PASSWORD`)이 있어도 에러 없이 무시 |
| `settings` | 앱 시작 시 한 번 생성되어 어디서든 `from app.core.config import settings`로 사용 |

**`.env`와 `.env.example`**
| 파일 | Git 관리 | 용도 |
|---|---|---|
| `.env` | ❌ (`.gitignore` 등록) | 실제 비밀번호 등 **개인 환경 값** |
| `.env.example` | ✅ | 어떤 변수가 필요한지 알려주는 **양식** |

```bash
cp .env.example .env    # 처음 클론 받은 뒤 각자 실행
```

> **왜 이렇게 하는가?** 이를 **12-Factor App**의 "설정은 환경에 저장한다(Config)" 원칙이라 한다. 코드는 그대로 두고 `.env`만 바꾸면 로컬·개발 서버·운영 서버에서 각각 다른 DB에 접속할 수 있으며, 비밀번호가 GitHub에 노출되지 않는다.

### 2-3. `pyproject.toml` — 프로젝트 메타데이터와 의존성 선언

Python 공식 표준(PEP 621) 형식의 프로젝트 설정 파일이다.

```toml
[project]
name = "ai-health-web-assignment"
requires-python = ">=3.13"
dependencies = [
    "alembic>=1.18.4",            # DB 스키마 마이그레이션
    "asyncmy>=0.2.11",            # MySQL 비동기 드라이버
    "cryptography>=46.0.6",       # MySQL 8 인증 방식(caching_sha2_password) 지원
    "fastapi[standard]>=0.135.3", # 웹 프레임워크 + uvicorn 등 표준 구성
    "pydantic-settings>=2.13.1",  # .env 기반 설정 관리
    "sqlalchemy[asyncio]>=2.0.49",# ORM (비동기 지원)
    "uuid6>=2025.0.1",            # UUID v7 생성 (시간 순 정렬 가능한 UUID)
]
```

| 항목 | 설명 |
|---|---|
| `requires-python` | 이 프로젝트를 실행하려면 Python 3.13 이상 필요 |
| `dependencies` | 필요한 라이브러리와 **허용 버전 범위** (`>=`: 이 버전 이상) |
| 관리 방법 | `uv add 패키지명` / `uv remove 패키지명` → 파일이 자동 수정됨 |

### 2-4. `uv.lock` — 의존성 잠금 파일 (Lock File)

`uv`가 의존성을 해석(resolve)한 결과로, **실제로 설치될 모든 패키지의 정확한 버전과 해시값**을 기록한다.

| 구분 | `pyproject.toml` | `uv.lock` |
|---|---|---|
| 작성 주체 | 개발자 (또는 `uv add`) | `uv`가 자동 생성 |
| 버전 표기 | 범위 (`fastapi>=0.135.3`) | 정확한 버전 (`fastapi==0.135.3`) |
| 대상 | 직접 사용하는 패키지만 | **하위 의존성까지 전부** (예: fastapi가 쓰는 starlette, pydantic) |
| 직접 수정 | ✅ | ❌ (절대 직접 수정하지 않음) |
| Git 관리 | ✅ | ✅ (반드시 커밋) |

```bash
uv sync    # uv.lock에 적힌 버전 그대로 .venv에 설치
```

> **왜 필요한가?** `fastapi>=0.135.3`만 적혀 있으면 A는 0.135.3, 몇 주 뒤 클론한 B는 0.140.0을 설치할 수 있다. 버전 차이로 생기는 "내 컴퓨터에서는 되는데요?" 문제를 막기 위해, 팀 전원이 **바이트 단위까지 동일한 환경**을 재현하도록 고정하는 것이 lock 파일의 목적이다.
>
> 📝 비유: `pyproject.toml`이 "우유 1L 이상"이라고 적힌 **장보기 목록**이라면, `uv.lock`은 "서울우유 1L, 바코드 880..."이 찍힌 **영수증**이다.

## 3. 데이터베이스 연결 설정

### 3-1. `app/core/db/databases.py` 전체 구조

```python
from sqlalchemy.ext.declarative import declarative_base
from sqlalchemy.ext.asyncio import AsyncSession, create_async_engine, async_sessionmaker
from typing import AsyncGenerator
from app.core.config import settings

# ① 접속 주소 조립
DATABASE_PREFIX = "mysql+asyncmy://"
DATABASE_URI = f"{settings.DB_USER}:{settings.DB_PASSWORD}@{settings.DB_HOST}:{settings.DB_PORT}/{settings.DB_NAME}"
DATABASE_URL = f"{DATABASE_PREFIX}{DATABASE_URI}"

# ② 비동기 엔진
async_engine = create_async_engine(DATABASE_URL, echo=False, future=True)

# ③ 세션 팩토리
AsyncSessionLocal = async_sessionmaker(bind=async_engine, autoflush=False, expire_on_commit=False)

# ④ 모델 베이스
Base = declarative_base()

# ⑤ 세션 의존성 함수
async def async_get_db() -> AsyncGenerator[AsyncSession, None]:
    async with AsyncSessionLocal() as db:
        yield db
```

### 3-2. 구성 요소 상세

#### ① 접속 주소 (Database URL)
```
mysql+asyncmy://ozcoding:pw1234@localhost:3306/ai_health
└─┬─┘ └──┬──┘   └──┬───┘ └─┬──┘ └───┬───┘ └┬─┘ └───┬───┘
 DBMS  드라이버   사용자  비밀번호   호스트   포트  DB 이름
```
- `mysql`: 사용할 DBMS 종류 (Dialect)
- `asyncmy`: 파이썬과 MySQL을 연결하는 **비동기** 드라이버
- 모든 값은 `config.py`의 `settings`, 즉 `.env`에서 가져온다.

#### ② 엔진 (`create_async_engine`)
DB와의 연결을 관리하는 핵심 객체로, 내부에 **커넥션 풀(Connection Pool)** 을 가지고 있다.
| 옵션 | 의미 |
|---|---|
| `echo=False` | `True`로 바꾸면 실행되는 SQL이 콘솔에 출력된다 (디버깅 시 유용) |
| `future=True` | SQLAlchemy 2.0 스타일 API 사용 (2.0부터는 기본값이라 생략 가능) |

> **커넥션 풀이란?** DB 연결을 맺는 작업은 비용이 크다. 요청마다 새로 연결하지 않고, 미리 연결 몇 개를 만들어 두고 **돌려쓰는** 방식이다.

#### ③ 세션 팩토리 (`async_sessionmaker`)
**세션(Session)** 은 DB와의 작업 단위(Unit of Work)로, "조회 → 변경 → commit"까지의 하나의 트랜잭션을 담당한다. `AsyncSessionLocal()`을 호출할 때마다 새 세션이 만들어진다.
| 옵션 | 의미 |
|---|---|
| `autoflush=False` | 쿼리 실행 전에 변경 사항을 자동으로 DB에 보내지 않는다. 개발자가 `flush`/`commit` 시점을 명시적으로 제어 |
| `expire_on_commit=False` | `commit` 후에도 객체 속성을 다시 조회하지 않고 그대로 사용할 수 있다. 비동기 환경에서 commit 후 속성에 접근할 때 발생하는 추가 쿼리(및 오류)를 방지 |

> 🚰 **비유**: 엔진은 건물에 한 번 깔아 두는 **수도관**, 세션은 요청이 올 때마다 꺼내 쓰고 반납하는 **컵**이다.

#### ④ `Base`
모든 ORM 모델이 상속하는 **부모 클래스**다. `Base`를 상속한 클래스들의 테이블 정보는 `Base.metadata`에 자동으로 수집되며, Alembic은 이 `metadata`를 보고 마이그레이션을 생성한다.

#### ⑤ `async_get_db()` — 의존성 주입(Dependency Injection)용 함수
```python
@router.get("/users/{user_id}")
async def get_user(user_id: str, db: AsyncSession = Depends(async_get_db)):
    ...
```
- FastAPI의 `Depends()`가 요청마다 이 함수를 실행해 **세션을 하나 만들어 API 함수에 넣어준다.**
- `yield` 이후 `async with` 블록이 끝나면서 **응답이 끝나면 세션이 자동으로 닫힌다.** 개발자가 세션 정리를 신경 쓸 필요가 없다.

### 3-3. 왜 비동기(async)인가
| 동기 (`def`) | 비동기 (`async def`) |
|---|---|
| DB 응답을 기다리는 동안 해당 작업자가 **멈춰 있음** | 기다리는 동안 **다른 요청을 처리** |
| 동시 요청이 많으면 대기열이 길어짐 | 적은 자원으로 많은 동시 요청 처리 |

DB 조회, 파일 업로드, 외부 AI 모델 호출처럼 **기다리는 시간(I/O)이 긴 작업**이 많은 웹 서버에서 비동기가 유리하다. 단, 비동기 함수 안에서는 DB 호출 앞에 반드시 `await`를 붙여야 한다.

### 3-4. 공통 Mixin (`app/core/db/models.py`)
여러 테이블에서 반복되는 컬럼을 미리 정의한 클래스로, 모델이 **다중 상속**하면 컬럼이 자동으로 추가된다.

| Mixin | 추가 컬럼 | 목적 |
|---|---|---|
| `UUIDMixin` | `uuid` CHAR(36), PK, 기본값 `uuid7()` | 순차 정수 ID(1, 2, 3...)는 전체 회원 수 추측·URL 조작이 가능하다. UUID는 예측이 어렵고, **v7은 시간순 정렬**이 되어 인덱스 성능도 좋다 |
| `TimestampMixin` | `created_at`, `updated_at` | 생성·수정 시각 기록 (운영 중 문제 추적에 필수) |
| `SoftDeleteMixin` | `deleted_at`, `is_deleted` | 행을 실제로 삭제하지 않고 "삭제됨" 표시만 한다. 의료 데이터처럼 **이력 보존이 중요한 도메인**에 적합 |

```python
class Patient(UUIDMixin, TimestampMixin, SoftDeleteMixin, Base):   # Mixin 먼저, Base는 마지막
    __tablename__ = "patients"
```

## 4. SQLAlchemy 모델 작성과 Alembic 마이그레이션

### 4-1. ORM이란
**ORM(Object-Relational Mapping)** 은 DB의 테이블을 파이썬 클래스로, 행(Row)을 객체로 다루게 해 주는 기술이다. SQL을 직접 작성하지 않고도 파이썬 코드로 DB를 조작할 수 있다.

| SQL | SQLAlchemy ORM |
|---|---|
| `CREATE TABLE users (...)` | `class User(Base): ...` |
| `SELECT * FROM users WHERE email = 'a@b.com'` | `select(User).where(User.email == "a@b.com")` |
| `INSERT INTO users ...` | `db.add(User(...))` |

### 4-2. 모델 작성 (SQLAlchemy 2.0 스타일)

```python
# app/models/user.py
from sqlalchemy import String, Enum
from sqlalchemy.orm import Mapped, mapped_column, relationship

from app.core.db.databases import Base
from app.core.db.models import UUIDMixin, TimestampMixin


class User(UUIDMixin, TimestampMixin, Base):
    __tablename__ = "users"

    email: Mapped[str] = mapped_column(String(50), unique=True, nullable=False)
    name: Mapped[str] = mapped_column(String(20), nullable=False)
    password: Mapped[str] = mapped_column(String(255), nullable=False)   # 해시값 저장
    phone: Mapped[str | None] = mapped_column(String(20))               # NULL 허용

    patients: Mapped[list["Patient"]] = relationship(back_populates="doctor")
```

```python
# app/models/patient.py
from sqlalchemy import ForeignKey
from sqlalchemy.dialects.mysql import CHAR


class Patient(UUIDMixin, TimestampMixin, Base):
    __tablename__ = "patients"

    name: Mapped[str] = mapped_column(String(20), nullable=False)
    doctor_uuid: Mapped[str] = mapped_column(CHAR(36), ForeignKey("users.uuid"))

    doctor: Mapped["User"] = relationship(back_populates="patients")
```

| 문법 | 의미 |
|---|---|
| `Mapped[str]` | 파이썬 타입 힌트. `str \| None`으로 쓰면 `NULL` 허용 컬럼이 된다 |
| `mapped_column(String(50))` | DB 컬럼 타입과 제약 조건 |
| `unique=True` | 중복 불가 (UNIQUE 제약 + 인덱스 생성) |
| `ForeignKey("users.uuid")` | DB 레벨 외래키. **`테이블명.컬럼명`** 으로 지정 |
| `relationship(back_populates=...)` | 파이썬 객체 레벨 연결. `patient.doctor`, `user.patients`처럼 접근 가능 (DB 컬럼은 생기지 않음) |

**ERD → 모델 변환 규칙**
| ERD 표기 | 모델 코드 |
|---|---|
| `varchar(50)` | `String(50)` |
| `int` | `Integer` |
| `text` | `Text` |
| `datetime` | `DateTime` |
| `boolean` | `Boolean` |
| `enum` | `Enum(파이썬Enum클래스)` |
| `not null` | `nullable=False` (또는 `Mapped[str]`) |
| `null` 허용 | `Mapped[str \| None]` |
| `pk` | `primary_key=True` (UUID라면 `UUIDMixin` 상속) |
| `ref: > users.uuid` (N:1) | `ForeignKey("users.uuid")` + `relationship()` |

### 4-3. `models/__init__.py`에 모델 등록 (필수)

```python
# app/models/__init__.py
from app.models.user import User
from app.models.patient import Patient
```

`alembic/env.py`는 다음과 같이 모델을 불러온다.
```python
from app.core.db.databases import Base, DATABASE_URL
from app import models          # ← app/models/__init__.py 실행
target_metadata = Base.metadata
```
모델 클래스는 **import되는 순간** `Base.metadata`에 등록된다. 따라서 `__init__.py`에 import하지 않은 모델은 Alembic 입장에서 **존재하지 않는 테이블**이 되어 마이그레이션 파일에 포함되지 않는다.

### 4-4. Alembic이란
**DB 스키마(테이블 구조)의 변경 이력을 버전으로 관리하는 도구**다. Git이 소스 코드의 변경 이력을 관리하듯, Alembic은 테이블 구조의 변경 이력을 관리한다.

| 상황 | Alembic 없이 | Alembic 사용 |
|---|---|---|
| 컬럼 추가 | 팀원 각자 DB에서 `ALTER TABLE` 직접 실행 | 마이그레이션 파일 하나를 공유, `upgrade head` 한 번으로 모두 반영 |
| 변경 되돌리기 | 수동으로 복구 | `downgrade -1` |
| 현재 DB 버전 확인 | 불가능 | `alembic current` |

### 4-5. 주요 명령어

> ⚠️ `alembic/env.py`가 `sys.path.append(os.getcwd())`로 경로를 잡기 때문에, 모든 명령어는 **`alembic.ini`가 있는 프로젝트 루트(`AH_web_development_assignment/`)에서 실행**해야 한다.

| 명령어 | 역할 | Git 비유 |
|---|---|---|
| `uv run alembic revision --autogenerate -m "create users table"` | 모델과 DB를 비교해 마이그레이션 파일 생성 | `git commit` |
| `uv run alembic upgrade head` | 최신 버전까지 DB에 반영 | `git pull` 후 적용 |
| `uv run alembic downgrade -1` | 직전 버전으로 되돌림 | `git revert` |
| `uv run alembic current` | 현재 DB에 적용된 버전 | `git status` |
| `uv run alembic history` | 마이그레이션 이력 | `git log` |

### 4-6. 마이그레이션 파일 구조
`revision --autogenerate`를 실행하면 `alembic/versions/`에 파일이 생성된다.

```python
# alembic/versions/a1b2c3d4_create_users_table.py
revision = "a1b2c3d4"          # 이 마이그레이션의 버전 ID
down_revision = None           # 직전 버전 ID (최초면 None) → 버전이 체인처럼 연결됨

def upgrade() -> None:         # 적용할 변경
    op.create_table(
        "users",
        sa.Column("uuid", mysql.CHAR(36), primary_key=True),
        sa.Column("email", sa.String(50), nullable=False),
        ...
    )

def downgrade() -> None:       # 되돌릴 때 실행
    op.drop_table("users")
```

> ⚠️ `--autogenerate`는 만능이 아니다. 컬럼 **이름 변경**은 "삭제 후 추가"로 인식해 데이터가 날아갈 수 있고, Enum 값 변경 등은 감지하지 못하기도 한다. **생성된 파일은 반드시 열어서 검토**한 뒤 `upgrade`한다.

DB에는 `alembic_version` 테이블이 자동 생성되어 **현재 적용된 `revision` 값**이 저장된다.

### 4-7. 전체 작업 순서

```
① 사전 준비
   - MySQL 실행 (Docker: docker compose up -d mysql / 또는 로컬·클라우드 MySQL)
   - .env에 DB 접속 정보 입력
② app/models/에 모델 작성
③ app/models/__init__.py에 import 추가
④ uv run alembic revision --autogenerate -m "create initial tables"
⑤ alembic/versions/ 의 생성 파일 검토 (upgrade/downgrade 내용 확인)
⑥ uv run alembic upgrade head
⑦ DB Viewer(DBeaver, MySQL Workbench, DataGrip 등)로 테이블 생성 확인
⑧ 모델 파일 + 마이그레이션 파일을 함께 커밋 → PR
```

### 4-8. 협업 시 주의사항
- **마이그레이션 파일은 모델과 함께 커밋한다.** 모델만 올리면 팀원들의 DB에 테이블이 생기지 않는다.
- **동시에 여러 명이 `revision`을 만들면 버전이 갈라진다(Multiple heads).** `down_revision`이 같은 파일이 두 개 생기기 때문이다.
  - 예방: 마이그레이션 생성 담당자를 정하거나, 반드시 최신 `main`을 pull 받은 뒤 생성한다.
  - 해결: `uv run alembic merge heads -m "merge"`
- **이미 `main`에 merge된 마이그레이션 파일은 수정하지 않는다.** 변경이 필요하면 새 마이그레이션을 추가한다. (Git에서 공유된 커밋을 수정하지 않는 것과 같은 원리)

## 5. API 구현 흐름

### 5-1. 요청의 생애주기 (Request Lifecycle)

`POST /api/v1/users` (회원가입) 요청이 처리되는 과정이다.

```
[Client] POST /api/v1/users  {"email": "...", "password": "..."}
   │
   ▼ ① 라우팅
[apis/user.py]        @router.post("") 함수가 요청을 받는다
   │
   ▼ ② 요청 검증
[schemas/user.py]     UserCreateRequest가 Body를 검증 ── 형식 오류 → 422 Unprocessable Entity
   │
   ▼ ③ 의존성 주입
[core/db]             Depends(async_get_db)가 DB 세션 생성
   │
   ▼ ④ 비즈니스 로직
[services/user.py]    이메일 중복 확인 ── 중복 → 409 Conflict
                      비밀번호 해싱
   │
   ▼ ⑤ 데이터 접근
[repositories/user.py] INSERT 실행, commit
   │
   ▼ ⑥ ORM 변환
[models/user.py]      User 객체 ↔ users 테이블 행
   │
   ▼ ⑦ 응답 직렬화
[schemas/user.py]     UserResponse로 변환 (password 제외)
   │
   ▼ ⑧ 응답
[Client] 201 Created  {"uuid": "...", "email": "..."}
   └ 세션 자동 종료
```

### 5-2. 구현 순서 — 안쪽(DB)에서 바깥쪽(API)으로

| 순서 | 파일 | 할 일 | 확인 방법 |
|---|---|---|---|
| 1 | `models/user.py` | 테이블 정의 | Alembic 마이그레이션 → DB Viewer |
| 2 | `schemas/user.py` | 요청·응답 형식 정의 | — |
| 3 | `repositories/user.py` | CRUD 함수 작성 | — |
| 4 | `services/user.py` | 비즈니스 규칙 작성 | — |
| 5 | `apis/user.py` | 엔드포인트 작성 | — |
| 6 | `main.py` | `include_router()` 등록 (`catch_all`보다 위) | — |
| 7 | Swagger | `/docs`에서 정상·예외 케이스 테스트 | 상태 코드, 응답 Body |

> 안쪽부터 만드는 이유: 바깥 계층은 안쪽 계층을 **호출**하기 때문이다. repository가 없으면 service를 완성할 수 없고, service가 없으면 api를 완성할 수 없다.

### 5-3. 계층별 코드 예시 (회원가입)

```python
# ① app/schemas/user.py
class UserCreateRequest(BaseModel):
    email: EmailStr
    name: str = Field(min_length=2, max_length=10)
    password: str = Field(min_length=8, max_length=20)

class UserResponse(BaseModel):
    uuid: UUID
    email: str
    name: str
    model_config = ConfigDict(from_attributes=True)
```

```python
# ② app/repositories/user.py
async def get_by_email(db: AsyncSession, email: str) -> User | None:
    result = await db.execute(select(User).where(User.email == email))
    return result.scalar_one_or_none()

async def create(db: AsyncSession, email: str, name: str, hashed_password: str) -> User:
    user = User(email=email, name=name, password=hashed_password)
    db.add(user)
    await db.commit()
    await db.refresh(user)          # DB가 채운 값(created_at 등)을 다시 읽어옴
    return user
```

```python
# ③ app/services/user.py
async def signup(db: AsyncSession, body: UserCreateRequest) -> User:
    if await user_repository.get_by_email(db, body.email):
        raise HTTPException(status.HTTP_409_CONFLICT, "이미 사용 중인 이메일입니다.")
    hashed = hash_password(body.password)
    return await user_repository.create(db, body.email, body.name, hashed)
```

```python
# ④ app/apis/user.py
router = APIRouter(prefix="/api/v1/users", tags=["users"])

@router.post("", response_model=UserResponse, status_code=status.HTTP_201_CREATED)
async def signup(body: UserCreateRequest, db: AsyncSession = Depends(async_get_db)):
    return await user_service.signup(db, body)
```

```python
# ⑤ app/main.py
from app.apis.user import router as user_router

app = FastAPI()
app.include_router(user_router)     # catch_all보다 위
```

### 5-4. 2일차 practice API와 비교

| 구분 | 2일차 practice API | 실제 프로젝트 구조 |
|---|---|---|
| 데이터 저장 | 메모리의 파이썬 리스트 (`user_list`) | MySQL DB |
| 서버 재시작 시 | 데이터 초기화 | 데이터 유지 |
| 파일 구성 | `practice_apis.py` 한 파일 | 5개 계층으로 분리 |
| 함수 | 동기 (`def`) | 비동기 (`async def` + `await`) |
| ID | 정수 자동 증가 (`max + 1`) | UUID v7 (`UUIDMixin`) |
| 비밀번호 | 평문 저장 | 해시값 저장 |
| 응답에서 password 제외 | `response_model` | `response_model` (동일) |

### 5-5. 상태 코드 사용 기준

| 코드 | 의미 | 사용 예 |
|---|---|---|
| `200 OK` | 성공 | 조회, 수정 |
| `201 Created` | 생성 성공 | 회원가입, 환자 등록 |
| `204 No Content` | 성공, 응답 본문 없음 | 삭제 |
| `400 Bad Request` | 잘못된 요청 (비즈니스 규칙 위반) | 수정할 항목이 하나도 없음 |
| `401 Unauthorized` | 인증 필요 | 로그인하지 않음 |
| `403 Forbidden` | 권한 없음 | 다른 사람의 정보 수정 |
| `404 Not Found` | 리소스 없음 | 존재하지 않는 환자 ID |
| `409 Conflict` | 리소스 충돌 | 이메일 중복 |
| `422 Unprocessable Entity` | 형식 검증 실패 | Pydantic 검증 오류 (자동) |

## 6. 템플릿 분석 중 발견한 주의사항

| # | 위치 | 내용 | 영향 | 권장 조치 |
|---|---|---|---|---|
| 1 | `core/db/models.py` `TimestampMixin` | `default=datetime.now(UTC)`처럼 **함수 호출 결과**를 기본값으로 지정 | 서버가 시작된 시각이 한 번만 계산되어, **모든 행의 `created_at`이 서버 시작 시각으로 고정**된다 (`onupdate`도 동일) | `default=lambda: datetime.now(UTC)` 또는 `server_default=func.now()`만 사용 |
| 2 | `core/db/databases.py` | `sqlalchemy.ext.declarative.declarative_base` 사용 | SQLAlchemy 2.0에서 deprecated (동작은 함, 경고 발생) | `from sqlalchemy.orm import declarative_base` 또는 `class Base(DeclarativeBase)` |
| 3 | `main.py` `catch_all` | 모든 GET 경로를 가로챔 | 라우터를 아래에 등록하면 API 대신 HTML 응답 | `include_router()`를 `catch_all`보다 위에 작성 |
| 4 | `alembic/env.py` | `from app import models`로 모델 로드 | `models/__init__.py`에 없는 모델은 마이그레이션 누락 | 모델 추가 시 `__init__.py` import 필수 |
| 5 | `alembic/env.py` | `sys.path.append(os.getcwd())` | 다른 폴더에서 실행하면 `ModuleNotFoundError: app` | `alembic.ini`가 있는 폴더에서 실행 |
| 6 | `.env` / `docker-compose.yml` | 로컬 실행 시 `DB_HOST=localhost`, 컨테이너 안에서는 서비스명 `mysql` | FastAPI를 Docker로 띄우면 `localhost`로는 MySQL에 접속 불가 | 실행 환경에 맞게 `DB_HOST` 변경 |
| 7 | `app/Dockerfile` | 빈 파일 | `docker compose up` 시 fastapi 서비스 빌드 실패 | 로컬 개발은 MySQL만 Docker로 실행 (`docker compose up -d mysql`), Dockerfile은 배포 단계에서 작성 |

> #1은 실제 데이터 정합성에 영향을 주는 이슈이므로, DB 모델 작성(:2-) 전에 팀 내에서 수정 여부를 논의하는 것을 권장한다.
