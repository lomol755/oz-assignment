## 3. 모델 분석과 방식 결정

### 3-1. 샘플 모델 파일 분석

과제가 제공한 샘플 모델 두 개를 PyTorch 없이 파일 내부 기록만 읽어 분석했다.

| 발견 | 근거 | 결정 |
|---|---|---|
| 구조는 SimpleCNN, 흑백 128×128 입력 | `Linear(32768, 2)`에서 32768 = 32채널 × 32 × 32, 풀링 2번이라 32 × 4 = 128 | 학습 때와 같은 전처리 필요 |
| GPU(`cuda:0`)에서 저장됨 | 텐서 위치 기록 | `map_location="cpu"` |
| **`model.pth`가 `__main__.SimpleCNN`을 참조** | 학습 노트북에서 정의한 클래스 | 서버에서 그대로 불러올 수 없음 → **`state_dict` + 클래스 재정의** 방식 |

> 모델을 통째로 저장하면 클래스의 "이름"만 기록된다. 학습 노트북의 `__main__`이 없는 서버에서는 불러올 수 없다는 점을 실제 파일로 확인했고, 이 결론이 팀장님 모델의 저장 방식에도 반영되었다.

### 3-2. 팀 모델 실측과 동기 방식 결정

팀장님의 EfficientNet-B0 5-fold 앙상블 가중치(각 15.6MB)로 실제 X-Ray를 CPU에서 10회 예측했다.

| 항목 | 결과 |
|---|---|
| 예측 | 정상, Confidence 83.28% (폐렴 확률 16.7%) |
| 추론 시간 | **평균 1.31초, 최대 1.46초** |
| 모델 5개 로딩 | 17.47초 (서버 시작 시 1회) |

| 동시 신규 요청 | 마지막 요청 예상 응답 | 판정 |
|---|---|---|
| 1건 | 약 1.6초 | ✅ |
| 2건 | 약 3초 | ⚠️ |
| 3건 이상 | 4.5초 이상 | ❌ |

팀원 한 명은 별도 worker 프로세스와 작업 테이블을 쓰는 **비동기 설계**를 제안했다. 하지만 측정 결과 한 건 기준으로 결과 표시까지 3초를 충족했고, 비동기는 화면 폴링·작업 테이블·임대 관리까지 필요해 하루 안에 구현하고 전원이 이해하기 어려웠다. 그래서 **동기 방식으로 확정**하고 비동기는 향후 과제로 남겼다. 같은 기록은 결과를 재사용하므로 추론이 겹치는 경우는 서로 다른 기록을 동시에 처음 예측할 때뿐이다.

## 4. 설계 문서 통합

팀원 5명이 각자 설계안을 쓰고 아래 세 기준으로 비교했다.

| 기준 | 이유 |
|---|---|
| API 주소가 프론트 코드와 같은가 | 다르면 구현해도 화면이 동작하지 않는다 |
| 같은 기록·같은 모델 재사용 규칙이 있는가 | 정의서 REQ-PRED-001의 핵심 |
| 히트맵을 선택사항으로 처리했는가 | DB `heatmap_url`이 NOT NULL이라 그대로는 저장할 수 없다 |

통합본에는 각 안의 장점을 모았다 (1·3단계 인터페이스 분리, `ai_model`·`model_version` 분리, 캐시 확인 후 모델 검사, 팀 이해 체크리스트 등). 리뷰 과정에서 다음 문제를 구현 전에 잡았다.

| 리뷰에서 잡은 문제 | 그대로 구현했다면 |
|---|---|
| `rollback()` 뒤 ORM 객체 속성 접근 | 비동기 세션에서 `MissingGreenlet` 에러 (409 판정 줄에서 발생) |
| commit 후 DB가 채운 `created_at` 접근 | 응답 직렬화에서 같은 에러 |
| `Decimal` confidence | JSON에 `"86.98"` 문자열로 응답 |
| SQLite는 `FOR UPDATE`를 무시 | 자동 테스트만으로는 잠금 동작을 보장할 수 없음 → MySQL 확인 항목 분리 |

## 5. ⑫ 예측 API 구현

### 5-1. 파일 구성

| 파일 | 내용 |
|---|---|
| `app/services/prediction_service.py` | 예측 서비스 (설계 6-1절 흐름) |
| `app/apis/prediction_apis.py` | POST 라우터, 201/200 분기, `Location` 헤더 |
| `tests/test_prediction_service.py` | 서비스 테스트 18개 |
| `tests/test_prediction_api.py` | API 테스트 7개 |

⑬(B)과 같은 파일을 고치면 충돌이 나므로 `prediction_*` 파일로 분리했다. A의 저장소 함수 이름(`get_current`, `add`, `refresh`)은 작업 전에 팀방에서 먼저 합의했다.

### 5-2. 처리 흐름

```text
1단계 읽기   진료기록 확인 → 같은 모델 결과 있으면 200 → 모델 없으면 503 → 최신 X-Ray·경로 검증
             → image_id·경로를 변수로 꺼낸 뒤 rollback
2단계 추론   동시 1개 제한 + 스레드풀. 손상 이미지 422 / 모델 오류 500
3단계 저장   환자 잠금 → 진료기록 잠금 → 이미지 ID 재확인(바뀌면 409)
             → add → commit → refresh → 201
             UNIQUE 위반(동시 요청이 먼저 저장) → 먼저 저장된 결과로 200
```

| 결정 | 이유 |
|---|---|
| **캐시 확인을 모델 확인보다 먼저** | 모델이 고장 나도 이미 저장된 결과는 응답할 수 있다 |
| **추론 전에 `rollback`** | SQLAlchemy는 첫 조회 때 트랜잭션을 자동으로 연다. 끝내지 않으면 1~2초의 추론 동안 DB 연결을 붙잡는다 |
| **rollback 전에 값을 변수로 꺼냄** | `rollback()`은 ORM 객체를 만료시킨다. 이후 속성에 접근하면 비동기 세션에서 에러가 난다 |
| **저장 시 잠금 + 이미지 ID 재확인** | 추론하는 사이 다른 사람이 X-Ray를 교체하면 예전 사진의 결과가 새 사진에 붙는다. 진료기록을 잠근 상태에서 확인해야 확인과 저장 사이에 교체가 끼어들 수 없다 |
| **UNIQUE를 최종 방어선으로** | 조회만으로는 두 요청이 동시에 "결과 없음"을 보고 둘 다 추론할 수 있다 |
| **동시 추론 1개 제한** | CPU 앙상블이라 요청이 몰리면 모두 느려진다 |
| **commit 이후 오류에서는 히트맵을 지우지 않음** | 이미 저장된 결과가 가리키는 파일을 지우지 않기 위해 `committed` 플래그로 구분 |

```python
image_id, image_url = image.id, image.image_url
await self.db.rollback()  # 읽기 트랜잭션 종료: 추론 동안 DB 연결·스냅샷을 붙잡지 않는다
...
latest = await self.records.get_image(record_id)      # 진료기록을 잠근 상태에서
if latest is None or latest.id != image_id:
    raise HTTPException(status_code=409, detail=IMAGE_CHANGED)
```

### 5-3. 기존 코드 재사용

5일차에 팀원들과 내가 만든 함수를 그대로 썼다. `patient_id_for`·`lock`(진료기록 수정·삭제 담당), `PatientRepository.lock`, `get_image`(내가 5일차에 만든 X-Ray 조회), `resolve_xray_path`(경로 검증). 잠금 순서도 5일차와 같은 **환자 → 진료기록**이라 교착 상태가 생기지 않는다.

## 6. 모델 연결 오류 복구

### 6-1. 문제

모델 연결 담당(D)의 PR #41이 `main`에 Merge되었는데, 파일을 불러오는 순간 에러가 나는 상태였다.

| 문제 | 결과 |
|---|---|
| `threading`, `time`, `logger`, `settings` import 누락 | `NameError` → 예측 API 전체 500 |
| `MODEL_NAME`, `MODEL_VERSION` 미정의 | C가 재사용 판단에 쓰는 이름이 없음 |
| NaN·범위 오류가 여전히 `ValueError` | 모델 고장이 "손상 이미지(422)"로 응답 |
| `predict_pneumonia`와 `__main__` 블록 중복 | 아래 정의가 위를 덮어씀 |
| `config.py` PR에 `Field` import 누락 | Merge하면 서버가 시작되지 않음 |

### 6-2. 해결

담당자와 협의해 C와 맞춘 수정본을 만들고, 실제 가중치로 검증해 #40에 포함했다.

| 수정 | 내용 |
|---|---|
| `worker/model.py` | `MODEL_NAME`·`MODEL_VERSION` 정의, import 보완, `is_loaded()`·`ensure_loaded()`·`load_default_model()`·`predict()`, 중복 제거 |
| 오류 종류 정리 | 모델 출력 오류 → `RuntimeError`(500), 이미지가 아닌 파일 → `ValueError`(422)로 통일 |
| `app/core/config.py` | `AI_PRELOAD_MODEL`, `AI_MAX_CONCURRENT_PREDICTIONS` |
| `app/main.py` | lifespan으로 서버 시작 시 모델 로딩, 실패해도 서버는 시작 |
| `prediction_service.py` | `AI_PRELOAD_MODEL=false`일 때 첫 요청에서 로딩 (그대로면 항상 503) |

> 검증 중 원래 모델 코드에서도 하나를 더 발견했다. 이미지가 아닌 파일이 Pillow의 `UnidentifiedImageError`로 나와 API에서 500이 될 상황이었다. 이를 `ValueError`로 감싸 설계대로 422가 되게 했다.

## 9. 배운 점

- **모델 파일은 "어떻게 저장했는지"가 배포를 좌우한다**: 통째로 저장한 모델은 학습 환경의 클래스 이름에 묶인다. 가중치(`state_dict`)와 코드를 분리해야 서버에서 안전하게(`weights_only=True`) 불러올 수 있다.
- **설계 결정은 측정으로 정한다**: 동기와 비동기 사이에서 고민할 때, 실제 추론 시간 1.31초라는 숫자가 결정을 단순하게 만들었다.
- **비동기 세션의 함정은 "만료"에 있다**: `rollback()`과 `commit()` 전후로 ORM 객체가 만료된다는 점을 모르면, 테스트 통과 후 운영에서 처음 터지는 버그가 된다.
- **동시성은 "확인 → 저장" 사이의 틈을 막는 일이다**: 잠금을 잡은 상태에서 확인해야 틈이 사라지고, DB 제약은 마지막 방어선이 된다.
- **오류의 종류도 API 계약이다**: 손상 이미지(422, 다시 해도 같음)와 모델 고장(500, 다시 시도 가능)을 예외 종류로 구분해야 화면과 운영자가 올바르게 대응한다.
- **협업에서는 "올라갔는지"를 직접 확인한다**: 로컬 수정과 push는 다르다. 리뷰는 화면 대신 브랜치를 받아 확인했고, 실수로 올린 파일은 기록에서까지 지웠다.
