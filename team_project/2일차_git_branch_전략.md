# Git Flow & GitHub Flow 브랜치 전략

> 참고: [Git Branch 전략 비교 - Git Flow vs GitHub Flow (SK DEVOCEAN)](https://devocean.sk.com/blog/techBoardDetail.do?ID=165571&boardType=techBlog)

## 1. 브랜치 전략이란?

프로젝트를 진행할 때 코드 버전 관리를 위해 주로 **Git**과 **GitHub**를 사용합니다.
여러 개발자가 하나의 저장소에서 협업할 때, **브랜치를 어떻게 만들고 합칠지에 대한 규칙과 작업 흐름(workflow)을 정해 두는 것**을 브랜치 전략이라고 합니다.
프로젝트의 성격에 맞는 전략을 고르는 것이 중요합니다.

### 브랜치 전략을 쓰면 좋은 점

| 이점 | 설명 |
|------|------|
| **독립적인 동시 작업** | 개발자마다 다른 기능 브랜치에서 작업하므로 서로의 작업이 영향을 주지 않습니다. |
| **작업 추적** | 브랜치가 특정 기능·이슈와 대응되어 어떤 작업인지 추적하기 쉽습니다. |
| **작업 단위 롤백** | 문제가 생기면 작업(브랜치) 단위로 되돌릴 수 있어 관리가 유연해집니다. |
| **버전 단위 배포 관리** | 태그(tag)를 이용해 원하는 버전 단위로 릴리스를 관리할 수 있어 배포 안정성이 높아집니다. |

대표적인 두 가지 전략이 **Git Flow**와 **GitHub Flow**입니다.

## 2. 브랜치 기본 명령어 (`git branch`)

### 📌 브랜치란?

- 브랜치는 **작업을 분리하는 독립된 작업 공간**입니다.
- 메인 코드에 영향을 주지 않고 기능을 개발할 수 있습니다.

### 📌 사용 예시

```bash
# 브랜치 목록 보기
git branch

# 브랜치 생성하기
git branch 브랜치명

# 브랜치 삭제하기
git branch -d 브랜치명
```

## 3. Git Flow

가장 **전통적으로 많이 쓰이는** 방식으로, 출시 버전·개발 버전·기능·출시 준비·버그 수정 등을 **역할별 브랜치로 나누어** 관리합니다.

### 브랜치 종류

| 브랜치 | 역할 |
|--------|------|
| `master` (`main`) | 제품 출시 버전을 관리하는 메인 브랜치 |
| `develop` | 다음 출시 버전을 위해 개발하는 브랜치 |
| `feature` | 새로운 기능을 개발하는 브랜치 |
| `release` | 다음 출시 버전을 준비하는 브랜치 |
| `hotfix` | 이미 출시된 제품의 버그를 고치는 브랜치 |

### 개발 흐름

```
feature ──▶ develop ──▶ release ──▶ master
                ▲                      │
                └────── hotfix ◀───────┘
```

1. 신규 기능 개발 시 `develop`을 기준으로 `feature` 브랜치를 만들어 작업합니다.
2. 작업이 끝난 `feature`는 `develop`에 병합(merge)합니다.
   - 실무에서는 보통 **Pull Request(PR)로 리뷰를 받은 뒤** 병합합니다.
3. 다음 출시를 준비하기 위해 `develop`에서 `release` 브랜치를 만듭니다.
   - 이 단계에서 발견된 버그는 **`release` 브랜치에서 바로 수정**합니다.
4. 충분히 테스트한 뒤, 정해진 주기(보통 배포할 버전 단위)로 `master`에 병합해 제품을 출시합니다.
5. 출시 후 `release`에서 걸러내지 못한 버그는 **`hotfix` 브랜치에서 바로 수정**합니다.

### 장점

- `release`, `hotfix` 브랜치를 통해 **배포 절차가 명확**합니다.
- **배포 안정성, 버전 관리, 롤백** 등 체계적인 운영이 가능합니다.
- 복잡한 프로젝트나 **대규모 팀**에 적합합니다.

### 단점

- 브랜치 종류와 과정이 많아 **복잡**합니다.
- 특정 기능이나 수정을 **빠르게 배포해야 할 때 유연성이 떨어집니다.**
- 작은 팀이나 개인 프로젝트에는 **불필요하고 부담스러울 수** 있습니다.

## 4. GitHub Flow

브랜치를 **하나의 기본 브랜치(`master`/`main`)** + **기능 추가용 브랜치(`feature`)** 두 가지만으로 운영하는 단순한 전략입니다. Git Flow보다 훨씬 간단하면서 **빠른 수정·배포**가 가능합니다.

배포는 Git Flow와 마찬가지로 `master`에서 하지만, `develop` · `release` · `hotfix` 같은 브랜치 없이 `feature` 브랜치만 존재합니다.

### 개발 흐름

```
master ──●─────────●─────────●──▶
          \       /  \      /
           feature     feature
          (PR → 리뷰 → merge → 배포)
```

1. `master`는 **배포용 소스코드**를 관리합니다. 새 기능이 필요하면 `master`에서 `feature` 브랜치를 만들어 작업합니다.
2. 작업이 끝나면 **`master`를 대상으로 Pull Request**를 만들어 리뷰를 요청합니다.
3. 리뷰가 끝나고 피드백이 모두 반영되면 `feature`를 `master`에 병합합니다.

### 실무에서 지키면 좋은 규칙

- `master`는 **항상 배포 가능한 상태**를 유지합니다.
- 브랜치 이름은 `feature/login`처럼 **작업 내용을 알 수 있게** 짓습니다.
- 병합 후에는 **바로 배포**하고, 작업이 끝난 브랜치는 삭제합니다.

### 장점

- 구조가 **단순**해서 배우고 적용하기 쉽습니다.
- **지속적인 배포**와 빠른 개발에 적합합니다.
- PR 기반이라 자연스럽게 **코드 리뷰 문화**가 자리 잡습니다.

### 단점

- 별도의 테스트·검증 단계 없이 바로 `master`에 병합되므로 **위험성**이 있습니다. (→ **테스트 자동화/CI**가 중요)
- 출시 버전을 따로 관리하지 않아 **여러 버전을 동시에 관리하기 어렵습니다.**
- 개발/스테이징/운영 등 **환경 구분이 명확하지 않고 규모가 작은 프로젝트**에 주로 적합합니다.

## 5. 한눈에 비교

| 구분 | Git Flow | GitHub Flow |
|------|----------|-------------|
| 브랜치 수 | 많음 (master, develop, feature, release, hotfix) | 적음 (master, feature) |
| 배포 방식 | `release` / `hotfix`를 통한 명확한 배포 절차 | `master`에서 단순·지속적 배포 |
| 복잡도 | 높음 | 낮음 |
| 안정성 | 높음 (검증 단계 존재) | 상대적으로 낮음 (바로 병합) |
| 배포 속도 | 느림 | 빠름 (Agile) |
| 버전 관리·롤백 | 체계적 | 약함 |
| 적합한 프로젝트 | 복잡한 프로젝트, 대규모 팀 | 작은 규모, 빠른 배포가 필요한 프로젝트 |

---

## 6. 어떤 전략을 선택해야 할까?

정답은 없고, 각 전략의 장단점이 있으므로 **프로젝트 규모, 요구사항, 팀의 작업 방식**에 맞춰 선택합니다.

- **Git Flow**: 더 많은 제어와 안정성이 필요하고 버전 단위로 출시하는 프로젝트
- **GitHub Flow**: 작은 팀·개인 프로젝트, 빠르게 만들고 자주 배포하는 프로젝트
