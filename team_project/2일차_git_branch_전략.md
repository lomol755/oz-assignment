# Git Branch 전략

## 1. 브랜치 전략이란?
여러 명의 개발자가 하나의 저장소에서 **서로 영향을 주지 않고 동시에 작업**하기 위해 정하는 브랜치 운영 규칙이다.

- 기능·이슈 단위로 작업을 나눠서 추적할 수 있다.
- 검증되지 않은 코드가 배포용 브랜치에 섞이는 것을 막는다.
- 버전 단위로 관리해서 배포의 안정성을 높인다.

대표적인 전략으로 **Git Flow**와 **GitHub Flow**가 있다.

---

## 2. Git Flow

### 개념
출시 버전, 개발 버전, 기능, 출시 준비, 버그 수정을 **각각의 브랜치로 나눠서** 관리하는 전략이다.

### 브랜치 종류
| 브랜치 | 역할 | 생성 위치 → 병합 위치 |
|---|---|---|
| `main` | 실제 배포되는 제품 버전 (항상 안정적) | - |
| `develop` | 다음 출시를 위해 기능을 모으는 개발 브랜치 | `main`에서 생성 |
| `feature` | 새로운 기능 개발 | `develop` → `develop` |
| `release` | 출시 전 QA, 버그 수정 등 배포 준비 | `develop` → `main`, `develop` |
| `hotfix` | 배포된 버전의 긴급 버그 수정 | `main` → `main`, `develop` |

### 작업 흐름
```
feature/login ──┐
feature/signup ─┼──▶ develop ──▶ release/1.0 ──▶ main (v1.0 배포)
                │                                  │
                └──────────────◀── hotfix ◀────────┘ (긴급 수정)
```
1. `develop`에서 `feature` 브랜치를 만들어 기능을 개발한다.
2. 기능이 완성되면 `develop`으로 병합한다.
3. 출시할 기능이 모이면 `release` 브랜치를 만들어 테스트와 버그 수정을 한다.
4. 준비가 끝나면 `main`과 `develop`에 병합하고 버전 태그를 붙인다.
5. 배포 후 급한 버그는 `main`에서 `hotfix` 브랜치를 만들어 수정한다.

### 장단점
- **장점**
  - 버전별로 체계적인 관리가 가능하다.
  - 개발 중인 코드와 배포된 코드가 명확히 분리된다.
  - 정기적으로 출시하는 대규모 프로젝트에 적합하다.
- **단점**
  - 브랜치 종류가 많아 복잡하다.
  - 병합 과정이 많아 배포 속도가 느리다.
  - 빠르게 자주 배포하는 서비스에는 과할 수 있다.

## 3. GitHub Flow

### 개념
하나의 기본 브랜치(`main`)와 기능 추가용 브랜치(`feature`) **두 종류만으로** 운영하는 단순한 전략이다.

### 브랜치 종류
| 브랜치 | 역할 |
|---|---|
| `main` | 항상 배포 가능한 상태를 유지하는 기본 브랜치 |
| `feature` | 기능 추가, 버그 수정 등 모든 작업 (이름은 작업 내용이 드러나게) |

### 작업 흐름
```
main ───●────────────●──────────●───▶
         \          /  \        /
          feature/A      feature/B
          (PR → 리뷰 → Merge)
```
1. `main`에서 작업용 브랜치를 만든다. (예: `feature/user-api`)
2. 코드를 작성하고 commit, push 한다.
3. GitHub에서 **Pull Request(PR)** 를 올린다.
4. 팀원이 코드 리뷰를 하고 승인(Approve)한다.
5. `main`에 병합(Merge)하고 바로 배포한다.

### 장단점
- **장점**
  - 구조가 단순해서 배우기 쉽다.
  - PR과 코드 리뷰 중심이라 협업에 집중할 수 있다.
  - 빠르고 자주 배포하는 서비스(웹 서비스, CI/CD 환경)에 적합하다.
- **단점**
  - 여러 버전을 동시에 관리하기 어렵다.
  - `main`이 항상 배포 가능해야 해서, 리뷰와 테스트가 부실하면 문제가 바로 배포된다.

---

## 4. 두 전략 비교

| 구분 | Git Flow | GitHub Flow |
|---|---|---|
| 브랜치 수 | 5종 (`main`, `develop`, `feature`, `release`, `hotfix`) | 2종 (`main`, `feature`) |
| 복잡도 | 높음 | 낮음 |
| 배포 주기 | 정기 출시 (버전 단위) | 수시 배포 |
| 적합한 프로젝트 | 대규모, 버전 관리가 중요한 제품 | 소규모 팀, 빠른 개발이 필요한 서비스 |
| 핵심 | 브랜치의 역할 분리 | PR과 코드 리뷰 |

## 5. 우리 팀의 선택
> **[GitHub Flow / Git Flow]** 를 사용한다. ← 팀 회의 후 하나만 남기기

### 선택 이유
- (예) 팀 규모가 작고 프로젝트 기간이 짧아 단순한 구조가 효율적이다.
- (예) PR과 코드 리뷰 과정을 통해 서로의 코드를 확인하며 협업을 연습할 수 있다.

### 우리 팀 브랜치 규칙
- 브랜치 이름: `feature/기능명` (예: `feature/patient-api`)
- `main` 브랜치에는 직접 push하지 않고 반드시 PR로 병합한다.
- PR은 팀원 1명 이상의 Approve를 받은 후 Merge한다.
- 작업 시작 전 `git pull`로 최신 코드를 받는다.

### 자주 쓰는 명령어
```bash
git checkout main                 # main으로 이동
git pull origin main              # 최신 코드 받기
git checkout -b feature/기능명     # 작업 브랜치 생성
git add .                         # 변경사항 담기
git commit -m "feat: 기능 설명"    # 커밋
git push origin feature/기능명     # 원격에 올리기 → GitHub에서 PR 생성
```
